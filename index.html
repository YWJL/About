agent-v8 | NestJS 网关 + Agent Worker 服务框架

个人项目 | 2026.09 - 至今

项目简介：面向 AI 平台的会话服务框架：把 LLM 会话拆成无状态 NestJS 网关与独立 Agent Worker，覆盖流式生成、工具调用、断线续订与并发保护。已按生产化标准落地：MySQL 作为唯一事实源承载事件日志、队列、会话快照与账本，Worker 可随时重启与扩缩容，崩溃后由其他 Worker 接管续跑。

技术栈：TypeScript / NestJS / SSE / Anthropic SDK / MySQL · Kysely / Docker

客户端—SSE→ NestJS 网关：鉴权 / 限频 / 排队进度 / 转发—HTTP→ Agent Worker × N：队列消费 / 工具 / 模型循环⇄ MySQL：队列 / 事件日志 / 账本

个人职责

  1. 框架分层：网关只保留鉴权、限频、参数校验、排队进度与 SSE 原样透传，会话、队列消费、模型循环、工具执行全部下沉到独立 Worker；两侧独立构建、发版、扩缩容，网关重启不影响在跑任务。
  2. 事件日志与恢复：MySQL 只追加事件日志（任务内 seq 即 SSE id）+ checkpoint 快照，按轮提交保证取消/失败不留脏数据；任意 Worker 都能按 seq 回放补齐断线，会话上下文可从任意 checkpoint 重建。
  3. 队列与路由：任务表即队列，按 conversationId 哈希分片，SKIP LOCKED 领取 + 会话互斥锁保证同会话串行；taskId → workerId 粘性路由，心跳超时快速失败，已结束任务任意 Worker 可回放。
  4. 幂等与账本：operationId 三层唯一键（发起任务 / 工具调用 / 记账），副作用工具按参数指纹跨重试去重；hold / settle / release 追加式账本 + 透支上限，按 max_tokens 预扣、按 usage 结算，重复结算不二次扣费。
  5. 故障接管：Worker 失联后由其他 Worker 条件抢占（worker_id + lease_epoch 做 fencing），释放旧预扣、追加 resumed 事件并按轮重跑；网关保持 SSE 连接，客户端看到 recovering → resumed 即无感续订。
  6. 工具运行时：tool_use → 执行 → tool_result 回填循环，控制最大轮数与结果截断；文件读写与命令执行统一做路径逃逸、符号链接校验、命令白名单和超时，执行中断按副作用标记 unknown 交模型决策。

项目业绩

  1. 双 Worker 压测 7.74 tasks/s（单 Worker 3.87，线性扩展）；3000 条排队连接下轮询仍线性（7.8k QPS），实测定位「排队位置查询随队列深度线性增长」为成本主因，关闭周期刷新后扫描行数 -79%。
  2. 自检覆盖 51 项端到端 + 50 项数据层（队列串行、幂等、账本、接管、恢复）；崩溃接管演示中杀掉执行中的 Worker，心跳 TTL 到期后由另一 Worker 接管同一 taskId，事件 id 连续、attempt=2 跑完，客户端无需重连。
  3. 压测反查出并发上限失效的调度 bug（派发到登记之间的窗口未计入并发，实际并发约为配置 2 倍），修复后吞吐与理论上限吻合到 81%；网关工程从 792 个 ts 文件裁剪到 233 个（-71%）。

bug-track | NestJS + gRPC 双栈微服务

个人项目 | 2026.09

项目简介：简化版 Bug 管理系统的微服务后端框架：两个平级服务各自同时暴露 HTTP 与 gRPC，bug-service 通过 gRPC 调用 file-service 完成附件上传与校验，用 txt 文件持久化替代数据库，重点验证服务契约、双通道错误语义和启动器抽象。

技术栈：NestJS / gRPC / pnpm workspace / class-validator / TypeScript / txt 文件持久化

个人职责

  1. 工程组织：用 pnpm workspace 管理 apps/bug-service、apps/file-service、libs/proto（共享 proto 契约）与 libs/common（双栈启动器、存储、异常过滤器、响应拦截器）。
  2. 跨服务附件链路：multipart 先进内存，Buffer 经 gRPC 转交 file-service，bug-service 只保存 FILE-id；ClientsModule.registerAsync 从环境变量组装客户端与 proto loader。
  3. 双栈一致性：connectMicroservice + inheritAppConfig 复用同一 IOC 容器和全局管道/过滤器；AllExceptionsFilter 按 host 类型分别产出 HTTP 响应与 gRPC status；txt 持久化用写串行队列避免并发覆盖。
  4. 启动器抽象：把 HTTP 端口、gRPC 地址、package 与 proto 路径收敛到 bootstrapHybridApp，新服务只需提供模块和参数即可同时具备两条通道。

项目业绩

  1. HTTP 与 gRPC 两条通道分别用 curl / grpcurl 验证通过，附件上传、查询、下载全链路跑通，跨服务调用毫秒级完成。
  2. gRPC 侧异常返回明确 status 而非 “2 UNKNOWN”，入参校验在两条通道同时生效；两个服务可用 pnpm dev 并行启动联调。
